# CS 255 Portfolio — DriverPass System Design

## Project Overview

This repository contains my CS 255 projects, including the **DriverPass Business Requirements Document** from Project One and the **System Design Document** from Project Two.

DriverPass is a company founded by Liam that aims to help students prepare for their driving tests and obtain their driver's licenses. The client wanted a system that would provide online learning materials, practice tests, and in-person driving lessons. The system would allow customers to create accounts, select packages, schedule driving lessons, and access practice tests. It would also help employees manage customer information, driving lesson schedules, and other administrative tasks.

The goal was to design a system that would make DriverPass's services easier to access while helping the company manage its operations efficiently.

## What I Did Particularly Well

I believe I did particularly well in identifying the system's main requirements and translating them into a structured design. I considered the different users of the system, including customers, employees, administrators, and IT personnel, and the different responsibilities each user would have.

I also used UML diagrams to represent the system from different perspectives. The use case diagram illustrates how users interact with the system, while the activity diagrams describe workflows such as scheduling a driving lesson and taking an online practice test. The sequence and class diagrams provide additional detail about system interactions and structure.

These diagrams helped organize the requirements and made the proposed system easier to understand.

## What I Would Revise

If I could revise one part of my work, I would improve the level of detail and consistency across the diagrams. I would make sure that each diagram clearly reflects the same requirements and that the relationships between system components are easy to follow.

I would also expand the design to explain how the system handles situations such as unavailable lesson times, invalid booking requests, and changes to scheduled lessons. Clarifying these scenarios would make the design more complete and demonstrate how the system should respond when something does not go as expected.

## Interpreting and Implementing User Needs

When designing the DriverPass system, I focused on the client's goal of providing convenient driving-test preparation services while simplifying the company's scheduling and administrative processes.

For example, customers need to schedule driving lessons without unnecessary difficulty. The design therefore considers lesson availability, drivers, vehicles, and the two-hour lesson slots described in the business requirements. Customers also need access to learning materials and practice tests that support their preparation for the DMV test.

Employees and administrators have different needs from customers, so the design also considers role-based access and administrative functions. Security is important because the system handles customer information and internal business data.

Considering user needs is essential because a system can function technically but still fail if it does not solve the problems it was created to address. Understanding users' goals helps ensure that the final product is practical, accessible, and aligned with the client's expectations.

## My Approach to Software Design

My approach to software design begins with understanding the problem and identifying the stakeholders. I then separate the requirements into functional requirements, which describe what the system must do, and nonfunctional requirements, which describe qualities such as security, reliability, and usability.

For DriverPass, I used UML diagrams to organize and communicate the proposed design. Each diagram served a different purpose, allowing me to examine user interactions, workflows, system behavior, and the relationships between classes.

In future projects, I would continue using this approach while placing greater emphasis on validating requirements with stakeholders and considering exceptions early in the design process. I would also use techniques such as user stories, prototypes, and additional workflow analysis to confirm that the design meets user expectations before implementation begins.

Overall, this project helped me understand the importance of translating business requirements into a clear, organized, and user-focused system design.
